# Discipline: data access

## What this covers
The database outlives every version of the code that writes to it. A schema edited by hand, a relation without a key, a price stored as a float or a time stored without its zone is a defect that survives releases, backups and rewrites, and the cost of fixing it grows with every row written in the meantime. These rules say what a table, a query, a transaction and a repository must look like so that the data stays correct when the code around it changes.
It is a file and not a prompt because a rule in a file binds the architect, the builder and the review alike, and a reviewer cites it by id.
Sources are the Microsoft Learn pages for EF Core and .NET data guidance, the PostgreSQL manual, martinfowler.com (Patterns of Enterprise Application Architecture, evolutionary database design), Evans and Vernon on aggregates and repositories, and the OWASP Cheat Sheet Series for injection.

## Rules
Rule ids are `DA-nn`. A finding cites one of them; the review scripts refuse an id that is not here.

### DA-01 The schema changes only through a versioned migration committed with the code; no hand edit on any environment
Why: a column added by hand on one database is missing on the next one, and nobody can say which version of the schema production runs. A migration file is the only record that can be reviewed, replayed and rolled back.
Source: Microsoft Learn, EF Core Migrations overview, https://learn.microsoft.com/ef/core/managing-schemas/migrations/; Fowler and Sadalage, Evolutionary Database Design, https://martinfowler.com/articles/evodb.html
Applies to: both

### DA-02 Every table has a primary key, and every relation is a foreign key with its delete rule written in the migration
Why: a table without a primary key cannot be updated safely or referenced at all; a relation without a foreign key accepts orphans; a foreign key without a stated delete rule falls back to whatever the provider and the ORM choose, and that choice differs between them.
Source: Microsoft Learn, EF Core Keys, https://learn.microsoft.com/ef/core/modeling/keys; Microsoft Learn, EF Core Cascade Delete, https://learn.microsoft.com/ef/core/saving/cascade-delete; PostgreSQL manual, Constraints, https://www.postgresql.org/docs/current/ddl-constraints.html
Applies to: both

### DA-03 Invariants that can be expressed as NOT NULL, UNIQUE or CHECK live in the database, not only in code
Why: application code is one writer among several (a script, a migration, a second service, a support tool); a constraint in the database holds for all of them, and a unique check done in code alone fails under two concurrent requests.
Source: PostgreSQL manual, Constraints, https://www.postgresql.org/docs/current/ddl-constraints.html; Microsoft Learn, EF Core Indexes and constraints, https://learn.microsoft.com/ef/core/modeling/indexes
Applies to: both

### DA-04 Money is stored as an integer in minor units or as a decimal with a fixed scale, with its currency, never as a floating-point number
Why: binary floating point cannot represent 0.10 exactly, so sums drift by cents and totals stop matching invoices; an amount without a currency is a number, not money.
Source: Fowler, Money pattern, Patterns of Enterprise Application Architecture, https://martinfowler.com/eaaCatalog/money.html; Microsoft Learn, floating-point numeric types in C#, https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/floating-point-numeric-types
Applies to: both

### DA-05 Instants are stored in UTC; where the user's local time matters, the offset or the time zone identifier is stored next to the instant
Why: a timestamp without a zone is ambiguous at every daylight-saving change and on every server with a different clock setting; an appointment at 09:00 Brussels time cannot be recovered from a UTC instant alone once the zone rules change.
Source: Microsoft Learn, Choosing between DateTime, DateTimeOffset, TimeSpan and TimeZoneInfo, https://learn.microsoft.com/dotnet/standard/datetime/choosing-between-datetime; RFC 3339, Date and Time on the Internet: Timestamps, https://www.rfc-editor.org/rfc/rfc3339
Applies to: both

### DA-06 Identifiers are generated by one rule for the whole system, and the rule is written in the ADR
Why: a project that mixes database sequences, client-side GUIDs and natural keys cannot merge data, cannot create an aggregate before it is saved, and leaks row counts where it uses sequences on public endpoints. One rule, chosen once, removes all three discussions.
Source: Microsoft Learn, EF Core Generated Values, https://learn.microsoft.com/ef/core/modeling/generated-properties; RFC 9562, Universally Unique IDentifiers (UUIDs), https://www.rfc-editor.org/rfc/rfc9562
Applies to: design

### DA-07 A use case loads what it needs in a bounded number of queries, never one query per row; the query count is measured in a test
Why: an N+1 pattern passes every unit test on ten rows and times out on ten thousand; the only reliable guard is a test that counts the statements a use case issues and fails when the count grows with the data.
Source: Microsoft Learn, EF Core Efficient Querying, https://learn.microsoft.com/ef/core/performance/efficient-querying; Microsoft Learn, Loading Related Data, https://learn.microsoft.com/ef/core/querying/related-data/
Applies to: code

### DA-08 Every index follows a query a use case actually runs, and the query is named in the migration or the ADR that adds the index
Why: an index nobody queries costs every write and helps no read; a query nobody indexed scans the table. Tying each index to a named query keeps both lists honest and lets a reviewer remove an index when the query goes.
Source: Microsoft Learn, EF Core Indexes, https://learn.microsoft.com/ef/core/modeling/indexes; PostgreSQL manual, Indexes, https://www.postgresql.org/docs/current/indexes.html
Applies to: both

### DA-09 A transaction spans one aggregate and one use case; cross-aggregate consistency is eventual and goes through an event or a saga, not a wider transaction
Why: a transaction that locks two aggregates serialises every user who touches either, and it deadlocks the moment two use cases take the locks in a different order. The aggregate is the consistency boundary; anything larger is a design decision that needs an ADR.
Source: Vernon, Implementing Domain-Driven Design, chapter 10, Aggregates (rule: modify one aggregate instance per transaction); Evans, Domain-Driven Design, chapter 6, Aggregates; Microsoft Learn, Designing a DDD-oriented microservice, https://learn.microsoft.com/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice
Applies to: design

### DA-10 A row a user edits carries a version column, and a save with a stale version is rejected with a concurrency error the user sees
Why: without it the second of two people editing the same record silently overwrites the first, and nobody finds out until the data is wrong. A version column turns the lost update into a visible conflict.
Source: Microsoft Learn, EF Core Handling Concurrency Conflicts, https://learn.microsoft.com/ef/core/saving/concurrency; Fowler, Optimistic Offline Lock, https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html
Applies to: both

### DA-11 SQL is never built by concatenating or interpolating values into a string; every value travels as a parameter
Why: one string built from user input is SQL injection, whatever the ORM around it; parameters also let the database cache the plan. Raw SQL is allowed only through the parameterised entry points the ORM provides.
Source: OWASP SQL Injection Prevention Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html; Microsoft Learn, EF Core SQL Queries, https://learn.microsoft.com/ef/core/querying/sql-queries; OWASP ASVS 5.0, chapter V1 Encoding and Sanitization, section V1.2 Injection Prevention
Applies to: code

### DA-12 A repository returns and accepts whole aggregates, exposes no queryable or ORM type, and has one implementation per store
Why: a repository that leaks `IQueryable` or the ORM's entity moves persistence decisions into every caller and makes the domain untestable without a database; a repository that returns a partial aggregate lets a caller break an invariant the aggregate exists to protect.
Source: Evans, Domain-Driven Design, chapter 6, Repositories; Fowler, Repository, https://martinfowler.com/eaaCatalog/repository.html; Microsoft Learn, Design the infrastructure persistence layer, https://learn.microsoft.com/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/infrastructure-persistence-layer-design
Applies to: both

### DA-13 Soft delete exists only where a requirement asks for it, with the retention period and the purge rule written next to it; otherwise a delete is a delete
Why: a soft-deleted row is still personal data under storage limitation, still counts in unique constraints, and still shows up in every query that forgets the filter. Without a retention rule it is kept forever by accident.
Source: Microsoft Learn, EF Core Global Query Filters, https://learn.microsoft.com/ef/core/querying/filters; Regulation (EU) 2016/679, Article 5(1)(e), storage limitation, https://eur-lex.europa.eu/eli/reg/2016/679/oj; the kit's `skills/legal-data-protection/SKILL.md`
Applies to: both

### DA-14 A backup counts only once it has been restored into a fresh environment by a scripted procedure, and the restore is repeated on a schedule written in the runbook
Why: a backup that has never been restored is a hope, not a backup; corrupt dumps, missing roles and wrong versions appear only at restore time, and the worst moment to learn that is the outage.
Source: Microsoft Learn, SQL Server Restore and Recovery Overview, https://learn.microsoft.com/sql/relational-databases/backup-restore/restore-and-recovery-overview-sql-server; PostgreSQL manual, Backup and Restore, https://www.postgresql.org/docs/current/backup.html
Applies to: both

### DA-15 Data written under an older schema version is converted by a migration step, never read by defensive code that tolerates both shapes
Why: a null check for "rows before version 12" lives in the code forever, doubles every test and hides the fact that the data is inconsistent. A data migration converts the rows once, and the code reads one shape.
Source: Fowler and Sadalage, Evolutionary Database Design, https://martinfowler.com/articles/evodb.html; Microsoft Learn, EF Core Managing Migrations, arbitrary changes via raw SQL, https://learn.microsoft.com/ef/core/managing-schemas/migrations/managing
Applies to: both

## What a reviewer checks
Questions to the design:
- Find the ADR line that names the id generation rule (DA-06) and the transaction boundary per use case (DA-09); flag a design that locks two aggregates.
- Check every entity in the data model for a primary key, every relation for a foreign key with a delete rule (DA-02), and every money or time field for its type and currency or zone (DA-04, DA-05).
- Confirm that each soft-delete flag points to a requirement with a retention period (DA-13) and that the runbook schedules a restore test (DA-14).
Questions to the diff:
- Read the migration before the code: the schema change is the contract the rest of the diff must honour (DA-01).
- Reject a schema change outside a migration file and a migration that only patches code around old rows (DA-01, DA-15).
- Look for a NOT NULL, UNIQUE or CHECK rule enforced in a validator but absent from the migration (DA-03).
- Search the diff for string concatenation or interpolation that reaches `FromSql`, `ExecuteSql` or a command text (DA-11), and for `IQueryable` or an ORM entity type on a repository signature (DA-12).
- Verify that a new index names the query it serves (DA-08), that a loop over results issues no query per iteration and that a query-count test covers the use case (DA-07), and that a user-editable table gained a version column (DA-10).

## Scenarios the tester writes
### Query count stays flat
Given an order list with 1 order and then with 200 orders
When the "list orders with customer names" use case runs against a database with statement logging
Then the number of SQL statements is the same in both runs (DA-07)

### Two editors, one row
Given two sessions that loaded the same customer with version 7
When the first saves and then the second saves without reloading
Then the second save fails with a concurrency error and the first change is still in the database (DA-10)
And the user of the second session sees a conflict message, not a generic error (DA-10)

### Injection probe through a search field
Given a search endpoint backed by a raw SQL query
When the search text is `'; DROP TABLE customers; --`
Then the query runs with the text as a parameter, returns zero rows, and the `customers` table still exists (DA-11)

### Money survives a sum
Given 10 line items of 0.10 in EUR
When the invoice total is computed and stored
Then the stored total is exactly 1.00 EUR and the column type is decimal with a fixed scale or an integer in cents (DA-04)

### Restore from last night
Given the latest backup file and an empty database server
When the scripted restore procedure runs
Then the application starts against the restored database and the migration history table shows the production schema version (DA-14, DA-01)
